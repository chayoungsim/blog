## 처음엔 속도만 보였다

AI 도구로 코드를 짜기 시작하면서 처음 눈에 들어온 건 속도였다. 반복적인 보일러플레이트나 CRUD 코드는 순식간에 나온다. 그런데 몇 주 지나고 보니, 정작 바뀐 건 속도가 아니라 **커밋 단위**였다.

## 왜 커밋을 더 잘게 쪼개게 됐나

AI가 만든 변경사항은 한 번에 여러 파일에 걸쳐 나오는 경우가 많다. 문제는 그 변경사항이 "의도한 것"인지 확인하는 절차 없이 그대로 쌓이면, 나중에 어디서부터 잘못됐는지 찾기가 훨씬 어려워진다는 점이다.

그래서 요즘은:

- 요청 하나 = 커밋 하나가 되도록 작업 단위를 미리 쪼갠다
- `git diff`로 실제 변경 내용을 항상 눈으로 확인하고 커밋한다
- 리뷰하기 애매하게 큰 변경은 "이 부분만 먼저 해줘"로 다시 나눠서 요청한다

```bash
git add -p   # 파일 전체가 아니라 청크 단위로 골라서 스테이징
git diff --staged   # 커밋 직전에 실제로 뭐가 바뀌었는지 마지막으로 확인
```

## 정리

AI가 "타이핑 속도"를 대신해주는 건 맞지만, "이 변경이 맞는지 판단하는 책임"은 여전히 내 몫이다. 그 판단을 제대로 하려면 결국 변경 단위를 작게 유지하는 오래된 습관이 더 중요해진다는 걸 체감했다.
